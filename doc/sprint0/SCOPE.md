# Cup Flow Coffee POS 第一阶段功能范围

## 1. 范围目标

第一阶段只验证咖啡 POS 的最小交易闭环：员工登录后可完成点单和收银，查询及处理订单；管理员可维护商品并查看简单经营数据。

完成标准为测试环境可走通：

`登录 → 商品选择与定制 → 创建订单 → 登记收款 → 查询/完成订单 → 看板核对`

## 2. 产品边界

| 维度 | 第一阶段边界 |
| --- | --- |
| 组织 | 单品牌、单门店 |
| 用户 | 收银员、管理员；账号由初始化数据提供 |
| 设备 | 桌面或触屏浏览器，最低目标分辨率 1280×800 |
| 订单渠道 | 店内收银台人工点单，可记录店内/外带 |
| 支付 | 现金、微信、支付宝、银行卡；仅登记收款结果 |
| 币种与语言 | 人民币、简体中文 |
| 网络 | 在线使用，不支持离线营业 |
| 数据 | 账号、菜单、订单、收款、操作日志和简单聚合指标 |

## 3. 第一阶段范围内

### 3.1 Must — 第一阶段上线必备

| 模块 | 包含能力 | 需求编号 |
| --- | --- | --- |
| 登录 | 登录、退出、预置账号、收银员/管理员权限 | AUTH-01 至 AUTH-03 |
| POS 点单 | 分类浏览、商品定制、购物车、计价、结算校验 | POS-01、POS-03 至 POS-06 |
| 收银 | 待支付订单、四种收款方式、收款记录、幂等 | PAY-01 至 PAY-05 |
| 订单 | 查询详情、作废、完成、管理员取消、状态审计 | ORDER-01 至 ORDER-06 |
| 商品后台 | 分类、商品、选项、上下架、售罄、历史快照 | PRODUCT-01 至 PRODUCT-04、PRODUCT-06 |
| 经营看板 | 当日销售额、订单数、客单价、取消额、商品 Top 10 | DASH-01 至 DASH-03 |
| 通用质量 | 事务一致性、错误提示、权限和关键操作日志 | SYS-01 至 SYS-03 |

| 模块 | 包含能力 | 需求编号 |
| --- | --- | --- |

## 4. 后续再设计的范围

下列能力不进入第一阶段需求分析、原型和开发。后续启动时需要独立补充业务规则、用户故事和技术评估。

### 4.1 门店作业

- 制作看板、分单、出杯状态、等待时长和叫号。
- 开班、交班、钱箱、班次对账和日结。
- 小票打印、标签打印、扫码枪和客显。

### 4.2 人员与组织

- 员工账号管理、密码重置、精细权限配置。
- 排班、考勤、多门店员工和总部组织架构。

### 4.3 商品与营销

- 套餐、第二杯优惠、满减和复杂价格规则。
- 会员、积分、等级、储值、优惠券和营销触达。
- 小程序、自助点单、外卖及第三方渠道。

### 4.4 库存与供应链

- 原料、配方、自动扣减、安全库存和售罄联动。
- 盘点、损耗、采购、入库、供应商和成本核算。

### 4.5 支付与财务

- 真实支付渠道、扫码支付、支付回调、退款和渠道对账。
- 组合支付、挂账、发票、财务凭证和会计系统集成。

### 4.6 平台能力

- 多门店、总部经营分析和跨店菜单管理。
- 断网收银、离线同步和冲突解决。
- 高级报表、毛利分析、经营预测和自定义报表。

## 5. 第一阶段迭代切分

| Sprint | 目标 | 核心交付 |
| --- | --- | --- |
| Sprint 1 | Figma UI 设计与工程基础搭建 | 全部核心页面设计、React/Java 工程骨架、数据库迁移、测试与 CI 基础 |
| Sprint 2 | 登录功能 | 登录、退出、初始化账号、登录态和角色权限 |
| Sprint 3 | POS 点单与收银功能 | 商品浏览与定制、购物车、服务端计价、订单创建和记账型收款 |
| Sprint 4 | 订单处理功能 | 订单查询与详情、作废、完成、管理员取消、状态机和审计 |
| Sprint 5 | 商品维护功能 | 分类、商品、选项、上下架、售罄和筛选 |
| Sprint 6 | 查看经营数据功能 | 经营指标、商品销量、日期筛选、收款构成及第一阶段验收 |

详细工作、依赖和完成标准以 [PRD 第一阶段实施计划](./PRD.md#11-第一阶段实施计划) 为准。迭代切分表示依赖顺序，不代表固定工期；最终排期以团队容量和故事点为准。

## 6. 前置决策

| 决策 | 默认方案 | Sprint 0 需要确认 |
| --- | --- | --- |
| 收款方式 | 现金、微信、支付宝、银行卡记账 | 是否需要删减方式或组合收款 |
| 现金找零 | Should 能力 | 是否提升为 Must |
| 订单完成 | 收银员手动完成 | 具体完成时点及是否允许批量操作 |
| 订单编号 | 单门店、自然日内唯一 | 编号格式和日切时间 |
| 取消处理 | 管理员取消，线下退款 | 权限、原因类型和退款责任人 |
| 商品选项 | 杯型、温度、糖度、加料 | 默认项、必选规则和加价规则 |
| 看板口径 | 已支付+已完成为有效订单 | 是否把未完成订单计入当日实收 |
| 目标环境 | 在线 Web 应用 | 设备、浏览器、部署与备份方案 |

若评审未作其他决定，开发按上述默认方案进行并记录为架构/产品决策。

## 7. 风险与控制

| 风险 | 影响 | 控制措施 |
| --- | --- | --- |
| 后续功能提前进入第一阶段 | 范围膨胀、延期 | 使用本文件作为变更基线，新增能力必须给出移出项或调整版本 |
| 前端与后端金额不一致 | 错账 | 后端为价格权威，金额使用最小货币单位并覆盖自动化测试 |
| 重复点击产生重复订单/收款 | 错账 | 幂等键、唯一约束和事务控制 |
| 并发订单状态冲突 | 数据异常 | 服务端状态机和乐观并发控制 |
| 取消口径与看板不一致 | 看板失真 | 统一有效订单定义，设计明细对账测试 |
| 商品变更污染历史订单 | 无法追溯 | 订单项保存商品、选项和价格快照 |
| 账号仅靠前端限制权限 | 越权 | 所有接口执行服务端鉴权和角色校验 |

## 9. Sprint 0 退出标准

1. 产品、研发和测试已评审三份文档，第一阶段 Must 范围无重大歧义。
2. 第 6 节的高影响决策已有明确结论、负责人和记录。
3. 六个核心模块的页面原型、状态和错误场景已评审。
4. Must 用户故事已拆分、估算、排序并建立可追踪的开发待办。
5. 数据模型、接口边界、权限模型、订单与收款状态机已评审。
6. 本地环境和 CI 可运行最小前后端应用及自动化测试。
7. Sprint 1 的目标、容量和完成定义已由团队确认。

## 10. 范围变更规则

- 新需求必须说明用户价值、优先级、验收标准和目标阶段。
- 影响第一阶段 Must 交付时，必须同步移出等量范围或调整排期。
- 后续功能不因数据模型“可顺便支持”而自动纳入页面、接口或验收范围。
- 已冻结规则发生变化时，需记录决定、影响模块和生效版本。
- PRD、用户故事、开发任务和测试用例使用需求编号建立追踪关系。
