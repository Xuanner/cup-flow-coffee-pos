# Cup Flow Coffee POS 产品需求文档（PRD）

| 项目 | 内容 |

| 产品名称 | Cup Flow Coffee POS |

## 1. 产品背景

咖啡店需要一套简洁的系统完成商品选择、饮品定制、收款、订单查询和营业数据查看。第一阶段优先打通最小交易闭环，验证 POS 的核心可用性，不同时建设制作、库存、会员和复杂门店管理能力。

## 2. 第一阶段目标

1. 员工可以安全登录，并根据角色访问收银端或管理端。
2. 收银员可以快速选择商品、配置规格并完成一笔订单。
3. 系统可以准确计算金额并登记收款结果。
4. 收银员和管理员可以查询订单，处理作废或取消。
5. 管理员可以维护分类、商品、规格、价格、上下架和售罄状态。
6. 管理员可以通过简单看板了解当日经营情况。

## 3. 本阶段非目标

以下能力不在第一阶段设计和开发范围内：

- 制作看板、叫号、出杯和后厨状态流转。
- 开班、交班、钱箱及班次对账。
- 员工账号后台、排班和考勤；首期账号通过初始化数据提供。
- 会员、积分、储值、优惠券、套餐和营销活动。
- 原料库存、配方扣减、盘点、采购和供应商。
- 真实微信、支付宝、银行卡支付接口及线上退款。
- 小票机、钱箱、扫码枪、客显等专用硬件集成。
- 多门店、总部后台、外卖平台和小程序点单。

## 4. 用户角色

| 角色 | 主要任务 | 第一阶段权限 |
| --- | --- | --- |
| 收银员 | POS 点单、收银、订单查询 | 访问收银台和订单；作废未支付订单 |
| 管理员 | 菜单维护、异常订单处理、经营查看 | 收银员全部权限；商品后台、订单取消和经营看板 |

第一阶段至少预置一个收银员账号和一个管理员账号，不提供员工账号管理界面。

## 5. 核心业务规则

- 一个订单包含一个或多个订单项，每个订单项保存下单时的商品名称、单价和定制快照。
- 商品售价由基础价、规格差价和加料价组成；所有金额由后端重新计算并校验。
- 商品支持杯型、温度、糖度和加料；不同商品可配置不同选项。
- 售罄或下架商品不可加入新订单。结算时若商品状态或价格已变化，需提示收银员重新确认。
- 第一阶段支付为记账型收款，支持现金、微信、支付宝和银行卡；系统记录收款结果，不调用真实支付渠道。
- 订单状态为：`待支付`、`已支付`、`已完成`、`已作废`、`已取消`。
- 收款成功后订单进入“已支付”，收银员可将已交付订单标记为“已完成”。第一阶段不跟踪制作过程。
- 待支付订单可由收银员作废；已支付或已完成订单只能由管理员取消，并必须填写原因。
- 取消仅记录业务结果，不自动执行资金退款；退款由门店线下处理。
- 订单号在门店和营业日内唯一；重复提交不得产生重复订单或重复收款记录。
- 金额以最小货币单位在后端存储，前端以人民币元展示。
- 经营看板只统计已支付和已完成订单；已取消订单金额单独展示，不计入有效销售额。

## 6. 核心流程

### 6.1 登录

1. 员工输入账号和密码。
2. 系统校验账号、密码和角色。
3. 收银员进入 POS，管理员默认进入管理端或自行切换模块。

### 6.2 POS 点单与收银

1. 收银员按分类浏览或按名称搜索商品。
2. 选择商品并配置规格、温度、糖度、加料、数量和备注。
3. 购物车实时展示订单明细和总金额。
4. 收银员创建待支付订单并选择收款方式。
5. 收款成功后展示订单号，清空购物车，可继续下一笔点单。

### 6.3 订单处理

1. 用户按订单号、日期或状态查询订单。
2. 查看商品快照、定制、金额、收款和状态信息。
3. 收银员可作废待支付订单或完成已支付订单。
4. 管理员可取消已支付/已完成订单并填写原因。

### 6.4 商品维护

1. 管理员维护商品分类和排序。
2. 管理员维护商品基础信息、价格、规格和加料。
3. 管理员控制商品上下架及临时售罄状态。
4. 变更只影响新订单，不修改历史订单快照。

### 6.5 查看经营数据

1. 管理员进入经营看板，默认查看当日数据。
2. 系统展示有效销售额、有效订单数、客单价、取消金额和商品销量排行。
3. 管理员可选择单个日期查看历史数据。

## 10. 非功能需求

### 10.1 性能与容量

- 正常网络下，常用页面首屏加载目标不超过 2 秒。
- 95% 的普通 API 请求目标响应时间不超过 500 毫秒；看板查询不超过 2 秒。
- 第一阶段支持单门店 5 个并发员工、每日 2,000 笔订单。

### 10.2 安全与一致性

- 密码使用安全哈希存储，登录态具备过期机制。
- 权限、金额和订单状态必须在后端校验。
- 订单创建、收款和状态变更使用事务、唯一约束及幂等控制。
- 日志不得记录密码、令牌等敏感信息。

### 10.3 易用性与兼容性

- 核心操作适配 1280×800 及以上桌面或触屏浏览器。
- 点单主流程提供加载、空状态、成功和错误反馈。
- 常用 POS 操作控件适合触控，防止连续点击产生重复交易。

### 10.4 可维护性

- 前后端接口使用统一版本、响应结构和错误码。
- 数据库变更使用版本化迁移脚本。
- 金额计算、订单状态机、权限和看板统计口径具备自动化测试。

## 11. 第一阶段实施计划

第一阶段规划为 6 个开发 Sprint。各 Sprint 应在开始前完成需求澄清和任务拆分，在结束时提供可演示、可测试的增量。具体周期和人员容量由团队估算后确定。

### 11.1 Sprint 1 — Figma UI 设计与工程基础搭建

**目标：** 完成第一阶段全部核心页面的交互设计，并建立可持续开发、测试和交付的 React + Java 工程基础。

**主要工作：**

- 在 Figma 中完成登录、POS 收银台、收款、订单列表与详情、商品分类管理、商品管理和经营看板的页面设计。
- 定义颜色、字体、间距、按钮、表单、表格、弹窗、状态标签和反馈提示等基础设计规范。
- 补齐加载、空数据、校验失败、无权限和服务异常等页面状态。
- 初始化 React 前端工程，建立路由、布局、状态管理、请求封装和基础组件结构。
- 初始化 Java 后端工程，建立分层结构、统一响应、异常处理、日志和配置管理。
- 确定数据库及迁移方案，建立本地开发环境、代码规范、自动化测试和 CI 基础流程。
- 形成鉴权、金额、订单状态、接口版本和错误码的技术设计。

**交付物：**

- 已评审的 Figma 页面、关键交互原型和基础设计规范。
- 可本地运行的前后端工程骨架及数据库连接。
- 开发环境说明、接口规范、数据库迁移和 CI 配置。
- 核心领域模型、订单状态机和第一版 API 清单。

**完成标准：**

- 产品、设计和研发已评审 Figma，六个核心模块无阻塞开发的交互缺口。
- 前后端应用可在本地和 CI 中构建、启动并执行基础测试。
- 前端可调用后端健康检查接口，数据库迁移可从空库成功执行。

### 11.2 Sprint 2 — 登录功能

**目标：** 建立可用的身份认证与角色权限基础，为后续所有业务模块提供访问控制。

**需求范围：** AUTH-01 至 AUTH-03、SYS-02、SYS-03 中与登录和权限有关的部分。

**主要工作：**

- 实现登录、退出、登录态保持与过期处理。
- 提供初始化的收银员和管理员账号，安全存储密码摘要。
- 实现前端受保护路由和基于角色的菜单展示。
- 实现后端统一鉴权、角色权限校验和未授权错误响应。
- 记录登录成功、失败和退出等必要安全日志。

**完成标准：**

- 收银员和管理员可登录并看到各自有权访问的入口。
- 错误密码、停用账号、过期登录态和越权接口请求均被正确拦截。
- AUTH 相关 Must 用户故事和自动化测试通过。

### 11.3 Sprint 3 — POS 点单与收银功能

**目标：** 打通从选择商品到登记收款的核心交易路径。

**需求范围：** POS-01 至 POS-06、PAY-01 至 PAY-06，以及 SYS-01、SYS-03 的相关部分。

**主要工作：**

- 实现分类浏览、商品搜索、商品定制、数量、备注和购物车。
- 实现前后端统一的商品状态、价格和金额校验。
- 创建待支付订单并生成单日唯一订单号。
- 实现现金、微信、支付宝和银行卡四种记账型收款。
- 实现现金实收与找零提示，并完成订单创建和收款幂等控制。
- 使用 Sprint 1 的迁移脚本或种子数据提供本 Sprint 所需菜单；商品后台维护界面在 Sprint 5 实现。

**完成标准：**

- 可使用初始化商品完整走通“加入商品—定制—购物车—创建订单—收款成功”。
- 商品状态或价格变化时，结算能够正确拦截并提示。
- 重复点击和请求重试不产生重复订单或重复有效收款。
- POS、PAY 相关 Must 用户故事及金额计算自动化测试通过。

### 11.4 Sprint 4 — 订单处理功能

**目标：** 让收银员和管理员能够查询、跟踪并处理交易订单。

**需求范围：** ORDER-01 至 ORDER-06、SYS-01、SYS-02。

**主要工作：**

- 实现按订单号、日期和状态查询订单。
- 实现订单详情及商品、定制、金额和收款快照展示。
- 实现待支付订单作废和已支付订单完成。
- 实现管理员取消已支付或已完成订单，强制填写取消原因。
- 实现服务端订单状态机、并发控制和关键操作日志。

**完成标准：**

- 所有合法状态流转可正常执行，跳跃状态、重复操作和越权操作均被拦截。
- 取消订单不会自动退款，并在界面明确提示线下处理。
- ORDER 相关 Must 用户故事、状态机和并发测试通过。

### 11.5 Sprint 5 — 商品维护功能

**目标：** 让管理员通过后台独立维护 POS 使用的菜单数据。

**需求范围：** PRODUCT-01 至 PRODUCT-06、SYS-02、SYS-03。

**主要工作：**

- 实现商品分类新增、编辑、启停和排序。
- 实现商品新增、编辑、上下架和条件筛选。
- 实现杯型、温度、糖度和加料配置及加价规则。
- 实现商品售罄与恢复在售。
- 验证菜单变更对 POS 新订单生效且不修改历史订单快照。

**完成标准：**

- 管理员无需修改数据库即可完成菜单日常维护。
- 收银员不能访问商品维护页面或接口。
- 上下架、售罄、价格和选项变更可在 POS 中正确生效。
- PRODUCT 相关 Must 用户故事和历史快照回归测试通过。

### 11.6 Sprint 6 — 经营数据功能与第一阶段验收

**目标：** 提供简单、可核对的经营数据，并完成第一阶段端到端验收和上线准备。

**需求范围：** DASH-01 至 DASH-05，以及第一阶段全部功能的集成与质量要求。

**主要工作：**

- 实现有效销售额、有效订单数、客单价、取消订单数和取消金额。
- 实现商品销量 Top 10、单日筛选和收款方式金额占比。
- 统一看板与订单列表的日期、状态和金额统计口径。
