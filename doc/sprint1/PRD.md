## 1. 文档目的

本文件定义 Sprint 1 的目标、需求、交付物和验收口径。Sprint 1 不交付登录、点单、收款等可用于营业的完整业务功能，而是为 Sprint 2 至 Sprint 6 建立两类基础：

1. 经评审、可开发的核心页面设计与交互规范。
2. 可构建、可测试、可持续扩展的前后端工程基础方案与实施任务。

本文档描述计划与验收基线，不代表相关设计或工程已经完成。

## 2. 背景与问题

Sprint 0 已明确第一阶段核心范围：登录、POS 点单、收银、订单管理、商品后台和简单经营看板。进入业务开发前仍需解决以下问题：

- 页面布局、关键交互、异常状态和角色差异尚未形成统一设计基线。
- 颜色、字体、间距、组件状态和触控尺寸尚未标准化，容易导致各模块体验不一致。
- React 与 Java 的工程结构、环境配置、接口约定、数据库迁移和测试方式尚未确定。
- 鉴权、金额、订单状态机、幂等和错误码等跨模块约束需要提前冻结。
- 缺少能够证明“前端—后端—数据库—CI”链路可运行的最小验证闭环。

## 3. Sprint 目标

### 3.1 产品与设计目标

- 完成第一阶段全部核心页面的高保真 UI 和关键流程原型。
- 建立满足桌面与触屏 POS 使用的基础设计规范和可复用组件清单。
- 覆盖正常、加载、空数据、校验失败、无权限、冲突和服务异常状态。
- 通过产品、设计、研发和测试联合评审，使后续 Sprint 无阻塞进入开发。

### 3.2 工程目标

- 明确 React + Java 工程的技术选型、目录结构、代码规范与版本基线。
- 规划并搭建前端、后端、数据库迁移、测试和 CI 的最小可运行骨架。
- 定义 API 版本、统一响应、错误码、环境配置和日志规范。
- 形成核心领域模型、订单状态机、权限矩阵和第一版 API 清单。
- 验证前端能够访问后端健康检查，后端能够连接数据库并从空库执行迁移。

## 5. 目标用户与设计原则

### 5.1 目标角色

| 角色 | 使用环境 | 核心诉求 |
| --- | --- | --- |
| 收银员 | 门店收银台，鼠标或触屏，高频连续操作 | 快速、清晰、防误触、交易反馈明确 |
| 管理员 | 门店电脑或收银设备 | 快速处理异常、维护商品、查看经营数据 |

### 5.2 设计原则

- **高频优先：** POS 主流程减少跳转，核心动作在首屏可见。
- **触控友好：** 主要点击目标建议不小于 44×44 px，危险操作避免紧邻高频操作。
- **状态明确：** 售罄、下架、待支付、已支付、已完成、已作废和已取消必须可快速区分。
- **金额醒目：** 应收、实收、找零和订单总额使用一致层级，金额统一保留两位小数。
- **失败可恢复：** 错误信息说明发生了什么、数据是否保存以及下一步可执行动作。
- **权限可理解：** 无权限操作不展示或置灰；直接访问时仍给出明确反馈。
- **一致可复用：** 相同语义的按钮、表单、弹窗、状态标签和反馈在各模块保持一致。

## 6. Figma UI 需求

### 6.1 文件与页面组织

Figma 文件建议按以下页面组织：

1. `00 Cover & Notes`：封面、版本、负责人、评审记录。
2. `01 Foundations`：颜色、字体、网格、间距、圆角、阴影、图标和可访问性说明。
3. `02 Components`：按钮、输入框、下拉、标签、表格、分页、弹窗、Toast、空状态等。
4. `03 Auth`：登录及登录异常。
5. `04 POS & Payment`：POS、商品定制、购物车、收款与结果。
6. `05 Orders`：订单列表、详情及状态操作。
7. `06 Products`：分类、商品、选项与状态维护。
8. `07 Dashboard`：经营概览、排行与收款构成。
9. `08 Prototype`：核心可点击流程。
10. `09 Handoff`：标注、资源、待决问题与开发交接说明。

### 6.2 核心页面清单

| 编号 | 页面/场景 | 必须包含 |
| --- | --- | --- |
| UI-01 | 登录页 | 账号、密码、登录、加载、错误、停用账号提示 |
| UI-02 | POS 收银台 | 分类、搜索、商品卡、售罄态、购物车、金额、结算入口 |
| UI-03 | 商品定制弹窗 | 杯型、温度、糖度、加料、数量、备注、必选校验、价格联动 |
| UI-04 | 收款弹窗 | 四种收款方式、应收金额、现金实收、找零、提交中与失败态 |
| UI-05 | 收款结果 | 成功/失败、订单号、继续点单、查看订单 |
| UI-06 | 订单列表 | 订单号、日期、状态筛选、列表、分页、加载与空状态 |
| UI-07 | 订单详情 | 商品快照、定制、金额、收款、时间线、权限相关操作 |
| UI-08 | 分类管理 | 列表、新增/编辑、排序、启停、校验和确认 |
| UI-09 | 商品管理 | 筛选、列表、新增/编辑、价格、上下架、售罄 |
| UI-10 | 商品选项配置 | 规格、温度、糖度、加料、默认值、加价与启停 |
| UI-11 | 经营看板 | 销售额、订单数、客单价、取消额、Top 10、日期筛选、收款构成 |
| UI-12 | 全局状态 | 404、403、会话过期、服务异常、断网提示、骨架屏、空状态 |

### 6.3 关键原型流程

- `登录 → POS 首页`。
- `选择商品 → 完成定制 → 加入购物车 → 修改数量/配置`。
- `购物车 → 选择收款方式 → 现金找零或非现金确认 → 成功/失败`。
- `订单列表 → 订单详情 → 作废/完成/取消确认`。
- `商品列表 → 新增/编辑 → 上下架/售罄`。
- `看板 → 切换日期 → 查看指标与排行`。

### 6.4 设计规范最低要求

| 类别 | 要求 |
| --- | --- |
| 颜色 | 品牌色、中性色、背景色及成功/警告/错误/信息语义色；标注对比度 |
| 字体 | 页面标题、模块标题、正文、辅助文字、金额和表格字号层级 |
| 间距 | 基于统一基础单位定义页面、组件和内容间距 |
| 组件 | Default、Hover、Focus、Pressed、Disabled、Loading、Error 等必要状态 |
| 响应式 | 以 1280×800 为最低目标，补充 1440 宽桌面布局规则 |
| 文案 | 中文业务用语统一，危险操作说明后果，错误提示包含恢复动作 |
| 交付 | 核心 Frame 使用 Auto Layout；组件与变体命名一致；开发可查看尺寸和属性 |

## 8. 跨模块技术设计交付

Sprint 1 需形成并评审以下内容：

- 角色权限矩阵：收银员与管理员的页面及接口能力。
- API 初版清单：认证、商品查询、订单、支付、商品维护和看板边界。
- 统一响应和错误码规范：业务失败、参数错误、未登录、无权限、冲突和系统异常。
- 金额规范：后端以最小货币单位存储与计算，前端仅负责展示和输入转换。
- 时间规范：数据库存储、接口传输和门店自然日的时区处理。
- 订单状态机：待支付、已支付、已完成、已作废、已取消及合法转换。
- 幂等策略：订单创建、收款和关键状态变更的幂等键、唯一约束和响应行为。
- 领域模型与 ER 图：账号、分类、商品、选项、订单、订单项、收款和操作日志。

## 9. 非功能需求

- 设计与工程以 1280×800 及以上桌面/触屏浏览器为基线。
- 常用页面首屏目标不超过 2 秒；普通 API P95 目标不超过 500 ms。
- 核心控件具备键盘焦点状态，状态不只依赖颜色表达。
- 密码、令牌和数据库凭证不得进入代码库或日志。
- 依赖版本可复现，数据库变更只能通过版本化迁移执行。
- 健康检查不得泄露数据库地址、凭证或内部堆栈。
- 金额、权限、状态机和幂等规则必须在后端执行最终校验。

## 12. Sprint 1 完成定义（DoD）

1. Figma 页面、组件、关键状态和原型满足本文件第 6 节，并完成联合评审。
2. 所有 Must 用户故事通过验收，缺陷和遗留项已记录优先级、负责人和目标 Sprint。
3. 前端、后端、数据库与 CI 的最小链路按开发说明可复现运行。
4. 代码质量检查与基础测试通过，不含真实凭证或敏感数据。
5. 技术设计交付物完成评审，关键决定有记录。
6. Sprint 2 登录开发所需页面、接口、数据和权限定义无阻塞歧义。
7. 文档中的“已完成”只在有对应设计、代码、测试或评审证据后勾选。
