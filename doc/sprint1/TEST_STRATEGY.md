# Cup Flow Coffee POS 测试策略与验收追踪

本文对应 `ENG-05`、`US-S1-ENG-03`，定义测试分层、自动化重点、稳定编号与 Sprint 1 基础链路
验收清单。测试的目标是尽早反馈、明确失败责任，并让需求、实现和证据能够长期追溯。

## 1. 测试分层与边界

| 层级         | 责任与适用范围                                                                        | 依赖边界                                                                       | 当前工具与入口                                        |
| ------------ | ------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------ | ----------------------------------------------------- |
| 前端组件测试 | 验证组件渲染、用户交互、表单/请求状态、键盘与 ARIA 语义；页面测试只覆盖前端可观察行为 | 使用模拟 HTTP 响应，不启动真实后端，不验证后端业务规则                         | Vitest、Testing Library；`npm run test`               |
| 后端单元测试 | 验证值对象、领域规则、计算和状态转换；重点覆盖边界值与非法输入                        | 不启动 Spring、不访问网络或数据库                                              | JUnit、AssertJ；`./mvnw test`                         |
| 接口测试     | 验证路由、HTTP 状态、统一响应、错误码、权限入口、追踪 ID 和接口级事务                 | 启动 Spring 测试上下文；数据库场景使用 Testcontainers，不依赖共享 Compose 数据 | JUnit、MockMvc、Testcontainers                        |
| 数据库测试   | 从空库执行 Flyway，验证约束、索引、基础数据、迁移兼容性和重复启动行为                 | 每个测试使用隔离的 PostgreSQL 容器；不连接开发者本地数据库                     | PostgreSQL 18.4、Flyway、Testcontainers               |
| 端到端测试   | 从浏览器验证少量跨前端、API、数据库的核心业务旅程和恢复路径                           | 使用专用可重置环境和测试数据；不替代组件、接口或领域层的穷举测试               | Sprint 2 接入浏览器 E2E 工具；CI 中独立于快速门禁运行 |

补充原则：

- 测试尽量放在能最早、最便宜发现错误的层级；同一规则不在 E2E 中穷举。
- 金额、权限、状态机、幂等和看板口径必须由后端做最终校验，前端测试只验证交互和反馈。
- 自动化测试不得依赖执行顺序、共享可变数据、个人凭证、真实支付渠道或生产服务。
- 单元/组件失败由所属模块维护者处理；接口/数据库失败由后端与数据变更作者处理；E2E 失败由
  旅程涉及模块共同定位，禁止仅以重跑掩盖不稳定用例。

## 2. 自动化优先级

| 优先级 | 领域       | 必须覆盖的风险                                                                | 进入条件                                                       |
| ------ | ---------- | ----------------------------------------------------------------------------- | -------------------------------------------------------------- |
| P0     | 金额       | 分转元、精度、舍入、数量/加料计算、折扣边界、应收实收与找零不变量             | 每个计价或收款故事合并前补齐单元与接口测试                     |
| P0     | 权限       | 收银员/管理员矩阵、未登录、越权、会话失效；前端隐藏入口不能替代后端拒绝       | 每个受保护接口必须同时覆盖允许和拒绝路径                       |
| P0     | 订单状态机 | 合法转换、非法转换、重复操作、取消条件、并发修改冲突                          | 状态转换实现时用参数化单元测试覆盖完整转换表，并有接口冲突测试 |
| P0     | 幂等       | 相同键同载荷重试、相同键不同载荷冲突、并发重复提交、响应重放                  | 创建订单、收款和关键状态变更接口上线前完成                     |
| P0     | 看板口径   | 有效销售额/订单、客单价、取消金额、Top 10、支付方式构成、门店自然日和时区边界 | 看板查询实现时使用固定数据集做数据库与接口断言                 |

当前 `MoneyTest` 已覆盖基础精度和整数运算，只是金额测试的起点；其余 P0 项在对应 Sprint 业务
故事进入开发时必须拆分为测试任务，不得推迟到上线前集中补测。

## 3. 稳定编号与追踪规则

### 3.1 编号格式

| 对象     | 格式                                 | 示例                                  |
| -------- | ------------------------------------ | ------------------------------------- |
| PRD 需求 | 仓库既有领域编号                     | `FE-07`、`BE-05`、`DATA-02`、`ENG-05` |
| 用户故事 | `US-S{Sprint}-{DOMAIN}-{NN}`         | `US-S1-ENG-03`                        |
| 开发任务 | `TASK-S{Sprint}-{DOMAIN}-{NN}-{NN}`  | `TASK-S1-ENG-03-01`                   |
| 测试用例 | `TC-S{Sprint}-{DOMAIN}-{NNN}`        | `TC-S1-HEALTH-001`                    |
| 验收证据 | `EVID-S{Sprint}-{DOMAIN}-{YYYYMMDD}` | `EVID-S1-ENG-20260820`                |

编号一经使用不得改义或复用。废弃项保留编号并标记 `Deprecated`；拆分产生新编号。开发任务、PR
标题或说明必须引用用户故事，测试代码的显示名称或测试说明必须包含 `TC-*`，验收记录必须写明
执行版本、日期、结果和证据位置。

执行命令：

```bash
cd backend/cup-flow-coffee-pos-java
./mvnw -Dtest=HealthEndpointTest test

cd ../../frontend/cup-flow-coffee-pos-web
npm run test -- src/features/system
```

### 4.2 完整链路人工复核

- [ ] `docker compose up -d postgres` 后 `docker compose ps` 显示 PostgreSQL `healthy`。
- [ ] `./mvnw spring-boot:run` 启动成功，日志不含数据库密码、Token 或内部堆栈响应。
- [ ] `curl --fail http://localhost:8080/api/v1/health` 返回 `SUCCESS`，应用和数据库均为 `UP`。
- [ ] `curl --fail http://localhost:8080/actuator/health` 返回 `UP`，不暴露数据库连接详情。
- [ ] `npm run dev` 后访问 <http://localhost:5173/system>，页面显示“后端服务运行正常”。
- [ ] 停止后端后重新检查，页面显示可恢复错误且不泄露内部详情；重启后端可恢复成功状态。

人工复核结果记录为 `EVID-S1-HEALTH-{YYYYMMDD}.md`，至少包含代码版本、执行环境、检查人、
各项结果和失败项链接；不得复制凭证到证据文件。

### 5.1 自动化用例


### 5.2 空库重建人工复核

该检查会删除专用验收环境的数据，只允许对已确认无业务数据的本地 Compose 项目执行：

- [ ] 确认当前目录为 `backend/cup-flow-coffee-pos-java`，且目标是本项目 Compose 环境。
- [ ] 执行 `docker compose down --volumes`，确认删除的是 `cup-flow-coffee-pos` 本地数据卷。
- [ ] 执行 `docker compose up -d postgres`，等待状态为 `healthy`。
- [ ] 执行 `./mvnw spring-boot:run`，确认 Flyway 从空库迁移到 V1，应用启动成功。
- [ ] 停止并再次启动后端，确认 Flyway 校验成功且不会重复创建对象或基础角色。
- [ ] 执行健康检查，确认数据库状态为 `UP`。
- [ ] 执行 `docker compose stop postgres`，保留证据所需环境或按团队约定清理。

人工复核结果记录为 `EVID-S1-DATA-{YYYYMMDD}.md`。任何已执行迁移脚本的 checksum 变化、重复
对象、缺少约束或基础数据重复都视为失败，必须通过新增迁移修复，禁止改写已发布迁移。

## 6. CI 与验收门禁

- Pull Request 必须通过 `Frontend` 和 `Backend` CI；失败步骤即初步责任边界。
- 快速门禁执行前端组件测试、后端单元/接口/数据库测试、静态检查和构建。
- E2E 接入后使用独立任务和可重置环境；P0 冒烟失败阻止合并，非 P0 不稳定用例必须有缺陷编号
  和修复期限，禁止长期无条件跳过。
- 需求验收前更新追踪矩阵并附 CI 链接或人工证据；缺少稳定 ID、预期结果或证据的项目不算完成。
