# Cup Flow Coffee POS — Sprint 1 用户故事

本文档覆盖 Sprint 1 的 UI 设计与基础工程能力。优先级采用 Must、Should；故事点由团队拆分技术任务后估算。所有验收应提供可查看的设计、代码、测试、运行记录或评审记录作为证据。

## 1. 设计基础与交接

### US-S1-UI-01 统一设计基础（Must）

**用户故事：** 作为产品与研发团队，我希望拥有统一的颜色、字体、间距、响应式布局和状态规范，以便各模块在手机、平板和网页端实现一致且可维护的体验。

**关联需求：** UI-FOUND-01

**验收标准：**

- Figma 中定义品牌色、中性色和成功、警告、错误、信息语义色。
- 定义字体(font family)、字重、页面标题、模块标题、正文、辅助文字、金额和表格字体层级。
- 定义基础间距、圆角、阴影、图标和页面网格规则。
- 定义手机、平板和网页端的响应式断点或容器规则，并说明各设备下的栅格、间距、字号和信息密度变化原则。
- Figma 至少提供手机、平板和网页端的代表性 Frame；网页端标注 1280×800 基线布局和 1440 宽布局原则。
- 明确导航、双栏/多栏、表格、弹窗等结构在窄屏下的折叠、堆叠、横向滚动或替代呈现规则，避免仅按比例缩放桌面稿。
- 状态信息不只依赖颜色，正文和关键控件对比度满足团队采用的可访问性标准。

### US-S1-UI-02 可复用组件与状态（Must）

**用户故事：** 作为前端开发者，我希望设计稿使用与 Radix UI 一致的可复用组件、交互语义和清晰变体，以便准确、高效地实现页面。

**关联需求：** UI-FOUND-02

**验收标准：**

- 通用组件优先与开发选用的 Radix UI Primitives 保持一致；至少覆盖按钮、输入框、选择器、搜索、标签、表格、分页、Dialog、Toast、空状态和加载状态。
- Figma 组件的命名、组成、变体、状态和交互行为与对应的 Radix UI 组件建立映射；Radix UI 未提供的组件或项目自定义差异需在设计说明中标注。
- 交互组件按需包含 Default、Hover、Focus、Pressed/Open、Disabled、Loading 和 Error 状态，并覆盖 Radix UI 对应的打开/关闭、选中/未选中等状态语义。
- 核心 Frame 使用 Auto Layout，组件、变体和图层命名可理解且一致。
- 组件支持手机、平板和网页端所需的尺寸或密度变体；主要触控操作目标建议不小于 44×44 px，例外项有明确理由。
- 键盘操作、焦点顺序、Focus Visible、关闭/取消方式及必要的 ARIA 语义与 Radix UI 的可访问性行为保持一致。
- 开发者可从设计文件读取尺寸、颜色、字体和间距属性，无需猜测。

### US-S1-UI-03 设计与代码 Token 映射（Should）

**用户故事：** 作为设计师和前端开发者，我希望设计 Token 与代码命名可映射，以便后续修改能够一致同步。

**关联需求：** HANDOFF-01、UI-FOUND-03

**验收标准：**

- 颜色、字体、间距和圆角提供建议的语义化 Token 名称。
- 文档记录设计变量与代码变量的映射方式和维护责任人。
- 至少用一个按钮和一个状态标签验证映射可行。

## 2. 核心页面设计

### US-S1-AUTH-01 登录体验设计（Must）

**用户故事：** 作为门店员工，我希望登录页面清楚反馈账号状态和登录结果，以便安全进入有权使用的模块。

**关联需求：** UI-AUTH-01、AUTH-01 至 AUTH-03

**验收标准：**

- 提供账号、密码、显示/隐藏密码、登录和提交中状态。
- 空字段能够显示字段级校验，且焦点移动到首个错误字段。
- 密码错误、账号不存在或停用使用不泄露账号信息的提示。
- 会话失效后可提示重新登录，并说明未完成操作是否保留。
- 登录成功后的收银员与管理员默认去向有明确标注。

### US-S1-POS-01 快速点单设计（Must）

**用户故事：** 作为收银员，我希望在一个清晰的工作区内浏览商品和管理购物车，以便快速完成连续点单。

**关联需求：** UI-POS-01、POS-01、POS-02、POS-04、POS-05

**验收标准：**

- 展示分类、搜索、商品名称、基础价和售罄状态。
- 商品区和购物车在 1280×800 下无需页面跳转即可完成主要操作。
- 售罄商品不可添加，空搜索和无商品分类均有空状态。
- 购物车支持数量、编辑、删除、清空、备注、小计和总额的设计。
- 空购物车不可结算；清空购物车有二次确认和清晰后果说明。

### US-S1-POS-02 商品定制设计（Must）

**用户故事：** 作为收银员，我希望准确选择商品规格与加料，以便记录顾客要求并在提交前发现遗漏。

**关联需求：** UI-POS-02、POS-03

**验收标准：**

- 设计覆盖杯型、温度、糖度、加料、数量和备注。
- 必选、单选、多选、默认值和不可用选项的视觉与交互明确。
- 加价选项能够即时反映到商品单价和合计。
- 缺少必选项时阻止加入购物车，并定位到缺失项。
- 编辑已有订单项时能够区分保存修改与新增商品。

### US-S1-PAY-01 收款与找零设计（Must）

**用户故事：** 作为收银员，我希望清楚选择收款方式并核对应收、实收和找零，以便避免现场收款错误。

**关联需求：** UI-PAY-01、PAY-02 至 PAY-06

**验收标准：**

- 提供现金、微信、支付宝和银行卡四种记账型方式。
- 现金方式显示应收、实收、快捷金额、输入校验和找零。
- 非现金方式明确实际渠道由门店线下确认，系统仅登记结果。
- 提交中防止重复操作；成功、失败和结果未知三类反馈可区分。
- 收款成功展示订单号、金额、方式、继续点单和查看订单入口。

### US-S1-PAY-02 价格或状态冲突设计（Must）

**用户故事：** 作为收银员，我希望结算时明确看到商品价格或售卖状态变化，以便安全确认或修改订单。

**关联需求：** UI-PAY-02、POS-06、SYS-01

**验收标准：**

- 指出发生变化的商品、原值和当前值。
- 售罄或下架时不可直接继续收款，并提供返回购物车处理的动作。
- 价格变化时明确新的订单总额及需重新确认的动作。
- 提示不会让用户误以为已产生订单或已完成收款。

### US-S1-ORDER-01 查询订单设计（Must）

**用户故事：** 作为收银员或管理员，我希望快速查找并理解订单详情，以便处理顾客咨询和交易异常。

**关联需求：** UI-ORDER-01、ORDER-01、ORDER-02

**验收标准：**

- 列表支持订单号、日期和状态筛选，并设计加载、空数据和失败状态。
- 状态标签能够区分待支付、已支付、已完成、已作废和已取消。
- 详情展示商品与选项快照、金额、收款、操作人和关键时间。
- 长订单、长备注和取消原因有明确展示规则。

### US-S1-ORDER-02 订单状态操作设计（Must）

**用户故事：** 作为有权限的员工，我希望在改变订单状态前看到条件和后果，以便减少误操作。

**关联需求：** UI-ORDER-02、ORDER-03 至 ORDER-06

**验收标准：**

- 待支付订单的作废、已支付订单的完成设计符合状态机。
- 管理员取消已支付或已完成订单时必须填写原因并二次确认。
- 取消设计明确“系统不自动退款，需线下处理”。
- 无权限、状态已变化和重复操作均有明确反馈，不提供非法继续入口。

### US-S1-PRODUCT-01 商品与分类管理设计（Must）

**用户故事：** 作为管理员，我希望高效维护分类、商品与售卖状态，以便 POS 使用准确的当前菜单。

**关联需求：** UI-PRODUCT-01、PRODUCT-01、PRODUCT-02、PRODUCT-04、PRODUCT-05

**验收标准：**

- 分类覆盖新增、编辑、排序、启停、重名校验和停用影响说明。
- 商品覆盖名称、分类、基础价、描述、上下架和售罄。
- 列表提供名称、分类和状态筛选，并有空数据、无结果和加载状态。
- 上下架和售罄状态在列表中易识别，危险或影响较大的操作需确认。

### US-S1-PRODUCT-02 商品选项配置设计（Must）

**用户故事：** 作为管理员，我希望配置商品可用的规格与加料，以便收银员只看到有效组合。

**关联需求：** UI-PRODUCT-02、PRODUCT-03、PRODUCT-06

**验收标准：**

- 覆盖杯型、温度、糖度、加料的名称、加价、必选、默认值和状态。
- 必选单选项至少有一个有效值，默认值必须属于有效选项。
- 无效组合和保存失败有字段级或模块级反馈。
- 设计说明配置变更只影响新订单，不修改历史订单快照。

### US-S1-DASH-01 经营看板设计（Must）

**用户故事：** 作为管理员，我希望快速理解当日核心经营指标，以便掌握门店经营情况。

**关联需求：** UI-DASH-01、DASH-01 至 DASH-05

**验收标准：**

- 展示有效销售额、有效订单数、客单价、取消订单数和取消金额。
- 展示商品销量 Top 10；无有效订单时显示解释性空状态。
- 日期选择不能选择未来日期，数据加载和查询失败有清晰反馈。
- Should 范围的收款方式构成可使用金额与占比展示，并与有效销售额口径一致。

### US-S1-SYS-01 全局异常与权限状态（Must）

**用户故事：** 作为系统用户，我希望在无权限、会话失效或服务异常时得到可恢复的反馈，以便知道下一步怎么做。

**关联需求：** UI-SYS-01、SYS-01、SYS-03

**验收标准：**

- 设计 403、404、会话过期、断网、服务异常和请求超时状态。
- 每个状态说明发生了什么、当前数据是否可能已保存以及可执行动作。
- 可重试与不可重试错误使用不同动作；重试不会暗示必然成功。
- 错误详情不展示堆栈、令牌或内部服务信息。

## 3. 前端工程基础

### US-S1-FE-01 可运行的前端骨架（Must）

**用户故事：** 作为前端开发者，我希望从固定版本和统一脚本启动项目，以便在一致环境中开发后续模块。

**关联需求：** FE-01、FE-02、FE-06

**验收标准：**

- 固定 Node、包管理器和主要依赖版本，并记录升级方式。
- 工程包含应用入口、路由、全局布局和六个核心模块的目录边界或占位路由。
- 提供开发、构建、静态检查和测试命令。
- 在干净环境按说明安装依赖后，构建和基础测试成功。

### US-S1-FE-02 统一请求与状态基础（Must）

**用户故事：** 作为前端开发者，我希望有统一的请求、错误和状态处理边界，以便各模块不重复实现基础逻辑。

**关联需求：** FE-03、FE-04、FE-07

**验收标准：**

- API 基础地址由环境配置提供，不硬编码生产地址。
- 统一解析成功、参数错误、未登录、无权限、冲突和系统异常响应。
- 明确服务端状态、跨页面客户端状态和局部 UI 状态的边界。
- 示例能够调用后端健康检查，并展示加载、成功和失败状态。

### US-S1-FE-03 设计系统接入基础（Must）

**用户故事：** 作为前端开发者，我希望以 Token 和基础组件承接 Figma 规范，以便后续页面保持一致。

**关联需求：** FE-05、UI-FOUND-01、UI-FOUND-02

**验收标准：**

- 颜色、字体、间距、圆角和语义状态使用集中定义的 Token。
- 通用交互组件基于 Radix UI 实现，并保留其键盘导航、焦点管理和 ARIA 等可访问性能力；样式通过项目 Token 扩展。
- 至少验证按钮、输入框、Dialog 和 Toast 的 Figma—Radix UI 映射及基础状态组织方式。
- 组件不把页面业务规则耦合进通用层。
- 键盘焦点、禁用、加载和错误状态可被测试或人工验证。

## 4. 后端与数据基础

### US-S1-BE-01 可运行的后端骨架（Must）

**用户故事：** 作为后端开发者，我希望通过固定 JDK 和统一构建命令启动服务，以便稳定开发业务能力。

**关联需求：** BE-01、BE-02、BE-05、BE-06

**验收标准：**

- 固定 JDK、构建工具和框架版本，并记录环境要求。
- 应用能够通过统一命令构建、测试和启动。
- 提供不泄露敏感信息的应用健康检查。
- 包或模块结构明确区分接口、应用、领域和基础设施职责，或记录采用的替代分层。

### US-S1-BE-02 统一 API 与错误处理（Must）

**用户故事：** 作为前后端开发者，我希望 API 使用统一版本、响应和错误码，以便可靠联调和排错。

**关联需求：** BE-03、BE-04

**验收标准：**

- 业务 API 使用 `/api/v1` 或评审批准的等价版本策略。
- 成功和失败响应结构包含稳定业务码、用户可理解消息、数据和请求追踪信息。
- 参数错误、未登录、无权限、资源不存在、状态冲突和系统异常有独立错误码。
- 未处理异常不向客户端暴露堆栈；日志可按追踪 ID 定位请求。
- 日志规范禁止记录密码、Token 和完整支付敏感信息。

### US-S1-DATA-01 可重复的数据库初始化（Must）

**用户故事：** 作为开发者和测试人员，我希望从空数据库通过版本化迁移获得一致结构，以便环境可以可靠重建。

**关联需求：** DATA-01 至 DATA-05

**验收标准：**

- 数据库产品及版本有明确记录，本地启动步骤可复现。
- 迁移脚本从空库执行成功，重复启动不会重复创建对象。
- 已执行迁移不得直接修改；变更通过新版本脚本完成。
- 金额、时间、主键、状态和审计字段规范有文档记录。
- 示例配置不含真实密码、Token 或个人连接信息。

### US-S1-BE-03 跨模块正确性方案（Should）

**用户故事：** 作为后端开发者，我希望提前定义鉴权、审计、幂等和并发扩展点，以便交易功能不会各自采用冲突方案。

**关联需求：** BE-07

**验收标准：**

- 记录鉴权上下文和角色校验的统一入口。
- 记录订单创建、收款和状态变化的幂等键行为与唯一约束建议。
- 记录订单状态变化的并发控制策略和冲突响应。
- 记录关键操作审计字段、触发位置和失败日志原则。

## 5. CI、质量与协作

### US-S1-ENG-01 新成员首次启动（Must）

**用户故事：** 作为新加入的开发者，我希望按照仓库说明启动完整基础环境，以便无需口头指导即可开始工作。

**关联需求：** ENG-01

**验收标准：**

- 说明列出必要工具、支持版本、环境变量、数据库、前端和后端启动顺序。
- 说明包含构建、测试、静态检查和常见故障排查。
- 由非作者在干净环境完成一次验证，并记录发现的问题。
- 不要求获取个人凭证才能运行本地基础链路。

### US-S1-ENG-02 持续集成基础（Must）

**用户故事：** 作为代码评审者，我希望每次提交自动验证构建、检查和基础测试，以便尽早发现回归。

**关联需求：** ENG-02、ENG-03

**验收标准：**

- 合并请求或团队约定的分支事件触发前端和后端检查。
- 至少执行依赖安装、静态检查、构建和测试；失败能够定位具体阶段。
- 依赖缓存不影响可复现性，锁文件或等价版本机制纳入检查。
- CI 日志不输出密码、Token 和数据库密钥。

### US-S1-ENG-03 测试策略与验收追踪（Must）

**用户故事：** 作为测试与研发团队，我希望明确不同层级的测试责任和需求追踪方式，以便后续 Sprint 可持续验证质量。

**关联需求：** ENG-05

**验收标准：**

- 说明前端组件测试、后端单元测试、接口测试、数据库测试和端到端测试的边界。
- 金额、权限、订单状态机、幂等和看板口径被标为后续自动化重点。
- PRD、用户故事、开发任务和测试用例使用稳定编号关联。
- Sprint 1 至少有健康检查和数据库迁移的验证清单。

### US-S1-ENG-04 协作规则（Should）

**用户故事：** 作为研发团队成员，我希望明确分支、提交和评审规则，以便多人协作时变更可追踪且容易回退。

**关联需求：** ENG-04

**验收标准：**

- 记录分支命名、提交信息、合并策略和最低评审要求。
- 数据库迁移、公共 API、依赖升级和设计 Token 变更需要指定评审人。
- 禁止直接提交真实密钥、大型构建产物和本地环境文件。

## 6. Sprint 1 验收故事

### US-S1-ACCEPT-01 联合设计评审（Must）

**用户故事：** 作为产品负责人，我希望产品、设计、研发和测试共同评审核心流程，以便后续开发不存在重大交互歧义。

**关联需求：** Sprint 1 DoD 1、2、6

**验收标准：**

- 按 PRD 页面清单逐项检查页面、状态和角色差异。
- POS 点单收款、订单处理和商品维护原型能够完整走查。
- 抽查核心流程在手机、平板和网页端代表性 Frame 中的布局与交互，确认不存在内容遮挡、关键操作不可达或仅依赖悬停的操作。
- 抽查通用组件与 Radix UI 的名称、状态、交互和可访问性映射；自定义差异均有记录并经设计与前端共同确认。
- P0/P1 设计问题在验收前关闭；其他问题有负责人和目标 Sprint。
- 评审结论、参加人、日期和主要决定可追溯。

### US-S1-ACCEPT-02 工程链路验收（Must）

**用户故事：** 作为技术负责人，我希望从干净环境验证完整基础链路，以便确认工程具备继续开发的条件。

**关联需求：** Sprint 1 DoD 3、4、5

**验收标准：**

- 前端与后端均能按说明构建、启动和执行基础测试。
- 前端成功访问后端健康检查，错误场景有明确反馈。
- 数据库迁移可从空库成功执行。
- CI 对同一版本代码执行成功，产出可定位的检查结果。
- 技术设计、API 草案和关键决策记录已完成评审。

## 7. 推荐优先顺序

1. US-S1-UI-01、US-S1-UI-02：先建立基础规范与组件规则。
2. US-S1-POS-01、US-S1-POS-02、US-S1-PAY-01、US-S1-PAY-02：先解决核心交易体验。
3. US-S1-AUTH-01、US-S1-ORDER-01、US-S1-ORDER-02：补齐身份与交易后处理。
4. US-S1-PRODUCT-01、US-S1-PRODUCT-02、US-S1-DASH-01、US-S1-SYS-01：完成后台、看板和全局状态。
5. US-S1-FE-01 至 US-S1-DATA-01：与设计并行建立工程基础。
6. US-S1-ENG-01 至 US-S1-ENG-03：完成可复现运行和质量闭环。
7. US-S1-ACCEPT-01、US-S1-ACCEPT-02：联合评审与 Sprint 2 交接。
